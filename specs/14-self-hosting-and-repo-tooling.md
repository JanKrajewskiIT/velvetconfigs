# Spec 14 — Self-Hosting & Repository Tooling

## Step 1 — Principle

The repository that produces the presets MUST consume them where reasonable. Self-hosting catches regressions early: a Prettier change that breaks consumer formatting also breaks the package's own format-check; an exports-map error caught by publint blocks publish.

The package consumes its presets where the repository has a matching source workload:

- ESLint — the repository lints its JavaScript modules through `eslint.config.mjs`. It does not consume the published factory because that would force the package to depend on its own published version during development.
- Stylelint — the package contains no CSS to lint.
- TypeScript — the package contains no compiled TypeScript implementation. Its `.d.mts` files are hand-authored declarations and are not emitted or type-checked by a repository build.
- Vite — the package itself is not bundled.

The package DOES consume its own Prettier preset, its own lint-staged config (a thin one, see Step 4), and its own Husky pre-commit hook helper.

## Step 2 — Repository scripts

The `scripts` block in `package.json` MUST define:

- `lint` — runs `eslint .` against the repository's JavaScript modules.
- `lint:fix` — runs `eslint . --fix` to apply safe ESLint fixes.
- `format` — runs `prettier --write .` against the repository.
- `format:check` — runs `prettier --check .` against the repository. CI uses this script.
- `verify` — chains `lint`, `format:check`, and `publint`. This is the single command that gates publish and CI.
- `prepublishOnly` — runs `verify`. Prevents manual `npm publish` from skipping validation.
- `prepare` — runs `husky`. Installs the package's pre-commit hook on `npm install`.

No `build` script exists. Every shipping artifact is hand-authored; there is no transformation step.

## Step 3 — Prettier wiring

- The `prettier` field in `package.json` points at `./prettier/index.json`. Running `format` or `format:check` reads the same JSON the preset publishes.
- The repository optionally adds a `.prettierignore` to skip generated files (`node_modules`, `coverage`, etc.). The exports map does NOT ship `.prettierignore`; ignore files are consumer-specific.

## Step 4 — Repository lint-staged config

The repository's own `lint-staged.config.mjs` is intentionally NARROWER than the preset it ships. Manual ESLint scripts cover the JavaScript modules, while the staged-file hook remains formatting-only. The repo config matches the relevant extensions and runs `prettier --write` against them.

The repository does NOT default-export the published preset for its own lint-staged config, because the published preset assumes a typical SolidJS app/library layout (sources under `src/`, CSS Modules, etc.) which the repo does not have.

## Step 5 — Repository Husky setup

A `.husky/pre-commit` file sources `husky/pre-commit.sh` (the same artifact the preset publishes). Two effects:

- The repository eats its own pre-commit hook.
- A regression in the pre-commit shell snippet trips on the next commit by a maintainer, surfacing immediately instead of only when a consumer upgrades.

## Step 6 — Repository `.gitignore`

At minimum, the repository ignores:

- `node_modules/`.
- The Husky managed-directory (`.husky/_`) which is generated by `husky install`.
- Test/coverage outputs if the repository ever grows tests.
- Editor and OS noise (`.vscode/`, `.idea/`, `.DS_Store`, etc.) per maintainer taste.
- The root `AGENTS.md` working copy — see Step 7.

The repository does NOT ignore `package-lock.json`. The lockfile is mandatory and used by `npm ci` in the verify pipeline.

## Step 7 — Agent guideline source and generated adapters

The repository has exactly one agent-guideline submodule, `.agents`, sourced from `https://github.com/JanKrajewskiIT/claude.git`. It is the canonical source for shared rules, skills, client settings, validation, and installation scripts. `.claude`, `.codex`, `.cursor`, `.github/skills`, `.github/instructions`, `.vscode/settings.json`, and root `AGENTS.md` are generated consumer views, not additional submodules.

Running `.agents/scripts/install-consumer.ps1` from the repository root without `-TargetRepository` targets the parent of `.agents`; an explicit target resolves to an absolute path. The script MUST reject a non-Git target and a target whose `.agents` path is not the script's owning guidance root. It supports PowerShell `-WhatIf` through `SupportsShouldProcess`.

The installer:

- Replaces root `AGENTS.md` and `.claude/CLAUDE.md` with one self-contained document assembled from `.agents/rules/*.md` in filename order, headed `# Shared Agent Guidance`.
- Removes an obsolete root `CLAUDE.md` when present so clients cannot discover two competing instruction files.
- Replaces complete skill trees under `.claude/skills`, `.codex/skills`, `.cursor/skills`, and `.github/skills` from `.agents/skills`.
- Replaces Claude, Codex, Cursor, and VS Code settings from the matching `.agents` templates.
- Generates Claude rule adapters with `paths`, Copilot instruction adapters with `name`, `description`, and optional `applyTo`, and Cursor `.mdc` adapters with `globs` or `alwaysApply`. React and Solid rules remain separate for Copilot/Cursor; Claude receives one TSX routing adapter that instructs the client to select exactly one framework.
- Adds every generated path to `.gitignore`, removes obsolete generated-ignore entries, removes generated files from the Git index with `git rm --cached --ignore-unmatch`, and leaves the generated files on disk.
- Writes generated text as UTF-8 without BOM and fails immediately on an error.

Generated locations are replacement-owned: project-specific content MUST NOT be stored in them. Only `.agents` is committed as a submodule. The generated paths and root `AGENTS.md` are ignored and regenerated by rerunning the installer after updating `.agents`.

None of the agent customization files, `.gitmodules`, or generated views ship in the package tarball because they are absent from the `files` allowlist.

## Step 8 — publint integration

`publint` is a devDependency invoked as part of `verify`. It validates:

- Every `exports` entry resolves to an existing file.
- Conditional exports declare conditions in the correct order (`types` before `import` / `require`).
- The `files` field actually includes every file referenced by `exports`.
- The package does not ship runtime files outside the `files` allowlist.

A publint failure must be treated as a release-blocker. The verify pipeline surfaces it before publish.

## Step 9 — README documentation contract

The README MUST contain at minimum:

- Install instructions including the consumer `.npmrc` entry required to reach GitHub Packages (or omit it if publishing to npmjs).
- A subpath-exports table enumerating every export and its purpose.
- One usage example per tool, demonstrating the recommended consumer wiring.
- The release workflow (bump → push → publish) so contributors do not need to read the workflow files.

The README is shipped (declared in `files`), so it accompanies the published tarball and is rendered on the registry page.

## Step 11 — Implementation order (recommended)

When applying these specs from scratch, follow this order so each step can be validated against the previous:

1. Specs 00 → 01: scaffolding, manifest, exports map.
2. Specs 03, 04, 05: static artifacts (Prettier, Stylelint, tsconfigs). Validate that publint accepts the exports map.
3. Spec 02: ESLint preset.
4. Specs 06 → 07: Vite factories.
5. Spec 08: lint-staged preset.
6. Spec 09: Husky helper.
7. Spec 10: Nginx config.
8. Spec 11: verify pipeline. Run on a draft PR.
9. Spec 12: publish pipeline. Test with a pre-release tag against a private channel before the first stable release.
10. Spec 13 → 14: codify versioning and self-hosting; ship the first stable release.

## Acceptance criteria

- `.gitmodules` contains one `.agents` entry and no generated client directory is configured as a submodule.
- A dry run of the installer reports the intended replacements without mutation; a real run reproduces all client views, ignores them, and removes any tracked generated copies while retaining them on disk.
- Running the installer twice from the same `.agents` revision is idempotent apart from line-ending normalization required by the script.
- Repository formatting, lint-staged, and Husky wiring consume the local shipped artifacts described above; unsupported self-lint/build surfaces are absent.
- Packing the npm package excludes `.agents`, generated client views, repository workflows, and `specs/`.
